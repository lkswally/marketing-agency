# ADR 0009 — MKT-3A: Campaign Strategy Engine

- **Status:** Accepted
- **Date:** 2026-05-29
- **Block:** MKT-3A
- **Supersedes:** —
- **Contracts:** `campaign-strategy.v1` (new, Pydantic, in
  `core/strategy/models.py`), `strategy-input-brief.v1` (input format).

## Context

MKT-2B left a usable runtime with a mock backend. MKT-2C settled the
external-data roadmap. The system could run workflows but not produce
anything useful end-to-end.

MKT-3A delivers the first real value loop: given a structured brief about
a client + product + audience + objectives, the system produces a complete,
reviewable, 20-section campaign strategy report. No LLM, no APIs.

## Decision

### D-9.1 — The engine is deterministic, LLM-free

Every output is generated by pure template functions in
`core/strategy/templates.py`. Same brief in → same report out (modulo
opaque ids and the `generated_at` timestamp).

Rationale:
1. Honors the safety posture established in MKT-2A/2B: no spawn, no API,
   no credentials in this block.
2. Lets the system be tested deterministically without recording fixtures.
3. Establishes the value loop and the data model now; promotion to
   LLM-backed generators is a separate block that requires the safety
   boundaries from `docs/runtime/agent-backend-safety.md` to be in
   place.

The trade is real: outputs are correct and complete but not creative.
That's the right trade for v1.

### D-9.2 — `core/strategy/` is a separate package

Alongside `core/runtime/`, `core/workflows/`, `core/contracts/`,
`core/agents/`, `core/skills/`, `core/memory/`. The strategy engine is
**one specific application** of those primitives, not part of the
primitives.

Same architectural principle as ADR 0006 D-6.1 (workflow specs in
`core/workflows/`, not `core/contracts/`).

### D-9.3 — `TemplatedStrategyBackend` routes by `(workflow_id, phase_id)`

The backend is an `AgentBackend` like any other (MKT-2B). When invoked
inside W7, it produces typed outputs by calling the matching template
generator and persisting the result. For any other workflow, it falls
back to `MockAgentBackend`.

Rationale: the backend can be wired as the default in any dispatcher
without breaking W1-W6, which still want generic mock envelopes.

### D-9.4 — Agent specs remain `status: spec_only`

The 16 agent specs from MKT-1E are not promoted to `implemented` by this
block. W7 references them by `agent_id` for documentation, but the
templated backend is the actual executor.

This avoids three failure modes:
1. Coupling agent identity to a backend that does not really invoke an LLM.
2. Forcing premature design of "what would a real `compliance-auditor`
   spawn look like".
3. Making the W7 workflow look like it relies on functionality (real
   LLM agents) that this block deliberately did not deliver.

Promotion of agent specs to `implemented` is still tracked as P-1E.3
and happens when real LLM execution lands.

### D-9.5 — The input brief is a versioned JSON file

Schema `strategy-input-brief.v1` validates with Pydantic before any
workflow runs. Required fields are minimal (`client`, `product`,
`objective`, at least one `audience_hints`). Everything else is
optional and surfaces in the diagnosis as "assumptions made".

Rationale: a strict shape would block real use; a too-permissive shape
would silently produce nonsense. The chosen middle keeps the reviewer
honest.

### D-9.6 — The markdown renderer is pure

`render_markdown_report(report: CampaignStrategyReport) -> str`. No I/O,
no template loading, no datetime. Same report instance → same string.

The 20 section titles are pinned in `_SECTION_HEADERS` and asserted
present by tests. Adding or removing a section is a breaking change to
the renderer and bumps `campaign-strategy.v2`.

### D-9.7 — Singleton id `"current"` for one strategy per client

Each strategy artifact is keyed by `(client_slug, kind, "current")`.
Re-running overwrites. Versioning strategies (history, A/B comparison) is
explicit future work.

Rationale: solving versioning here would add Approval Center wiring,
state machine, naming. The block intentionally stops short of that to
deliver the report shape first.

### D-9.8 — The dispatcher is unchanged

W7 runs through the existing `MinimalDispatcher` (MKT-2A) with the
templated backend injected. No new dispatcher, no new contracts on the
runtime side, no new audit event types beyond what MKT-2A already emits.

This is the leverage of MKT-2A's minimal-but-complete dispatcher: it
absorbs a real application without changes.

### D-9.9 — Claim audit is NOT enforced in MKT-3A

Section 19 of the report enumerates unverified claims and flags
`requires_compliance_audit: true`. But the compliance gate (`claim_strict`
mode, `g_compliance_passed`) is NOT applied to the report or its
artifacts.

Rationale: the report's claims are template-derived from the brief; they
will be more meaningful (and more in need of audit) once an LLM
generates them. MKT-3B is the right block to wire claim audit into the
strategy flow, against the eventual LLM output.

The hooks are in place: the report has a `RiskAssessment`, the workflow
emits `g_approval_packaged`, the Approval Center spec already covers the
state machine.

### D-9.10 — Image prompts, not images

The `CreativeBriefPack` produces ready-to-paste prompts for an image
generation model. The block does NOT call any image API.

Rationale: image generation is its own integration arc (cost, IP, brand
safety, hosting). Strategy is a separate concern; the engine produces
the brief for the image, not the image itself.

### D-9.11 — Output file at `outputs/<client_slug>/campaign-strategy.md`

The directory is configurable via `--outputs-dir`. The filename is fixed.
The path is gitignored (per `.gitignore` `outputs/*` rule from MKT-1A).

Rationale: deliverables belong outside the repo. A reviewer copies the
file to share with the client; the system does not commit deliverables.

### D-9.12 — `mkt run-strategy` is the only new CLI surface

No `mkt strategy preview`, no `mkt strategy diff`, no `mkt strategy
publish`. Future affordances are tracked in PENDING; v1 ships the one
command that closes the loop.

## Alternatives considered

- **LLM-backed generation now.** Rejected — requires the safety
  boundaries from `agent-backend-safety.md` to be in place, which is a
  separate block with its own approval. The deterministic engine
  establishes the data model and value loop without touching that gate.
- **Render the report on the fly without persisting the model.**
  Rejected — the persisted Pydantic model is the auditable artifact;
  Markdown is a presentation of it. Future blocks (Portal, claim audit
  enforcement) consume the model, not the Markdown.
- **One mega-module `core/strategy.py`.** Rejected — five focused
  modules (models, templates, backend, pipeline, renderer) keep
  diffs small and let each surface be replaced independently.
- **Make the backend extend `MinimalDispatcher` instead of
  `AgentBackend`.** Rejected — `AgentBackend` is the abstraction MKT-2B
  built. Reusing it keeps W7 in the same dispatching shape as W1-W6.
- **Pin a longer-lived id (e.g. `strategy_v1`) instead of `"current"`.**
  Rejected — the v1 use case is "one strategy per client at a time";
  versioning is its own block when the demand appears.

## Consequences

- The system can be demoed end-to-end: provide a brief, run one
  command, get a deliverable.
- Tests cover 60+ structural and determinism cases; the suite grows
  from 311 to ~396 with this block.
- Future blocks have a complete output model to consume. Approval
  Center, claim audit, Portal, LLM-backed generation all plug in on top.
- The repo now has a deterministic ground-truth for what "good output"
  looks like. When LLM-backed generators ship, they can be regression-
  tested against this baseline.

## Out of scope for MKT-3A

- LLM-backed generators (dedicated block, requires safety boundaries).
- Real claim audit enforcement on the report (MKT-3B).
- Approval Center halt-and-wait flow (post-MKT-3B).
- Real image generation (post-MCP / Replicate integration).
- Versioned strategies per client.
- Parallel phase execution.
- Live data sources for keywords, competitor benchmark, audience
  sizing (post-MCP-3/4/5).
- Email send / social publish (MKT-MCP-8 via n8n).
- A `mkt strategy diff` / preview / publish CLI surface.
